# Shaders and materials

## Why shader inspection is required

Texture format is not material meaning. Frostbite material metadata and shader
database entries determine:

- which resource is bound to each slot;
- which UV set and scale are used;
- channel swizzles;
- color-space treatment;
- tangent-space reconstruction;
- how detail normals are combined with the base normal.

The PC complete-map importer now performs mesh-to-shader-database association
for resolved static surfaces. It preserves every recovered binding, reflects
pixel-shader resource names, and builds source-driven Blender graphs. This is
not equivalent to recovering arbitrary shader arithmetic: the MedKit
`plastic` surface below remains the only path whose complete detail-normal
calculation has been reproduced exactly.

## PC DX11 shader database

The implemented reader parses parameter groups, material keys, texture binding
indices, compiled vertex/pixel shader records, and `RDEF` resource bindings.
Shader declarations and non-reflection bytecode chunks are structurally
consumed but are not retained. On the tested `MP_001` database:

| Measurement | Result |
|---|---:|
| File size | 26,905,158 bytes |
| Material keys | 8,222 |
| Unparsed trailing bytes | 0 |

Material lookup is case-insensitive. Binding indices are preserved; list order
is not substituted for the original `tN` slot. Each material binding also
retains all reflected pixel-shader parameter names observed across its linked
rendering permutations. This distinguishes names such as
`texture_Texture`, `texture_RepeatingNormalMap`,
`texture_Layer1_Detail2`, and `texture_OcclusionTexture`.

Three tested Barrack DBX surfaces use `cheap_Wood`, `cheap_WoodPlanks`, and
`cheap_MetalStairs` partition names while the same mesh's shader database keys
omit the `cheap_` prefix. If exact lookup fails, the importer tries that one
narrow alias and records both requested and resolved keys. It does not apply
general fuzzy shader-key matching.

The resolved key is constructed from the mesh asset `Name`, `/`, and the
surface shader partition path:

```text
mesh asset Name + "/" + surface Shader partition
```

This form is verified across the `MP_001` static mesh set, not just inferred
from a texture filename. See
[`shaderdb.py`](../bc2_frostbite_importer/core/shaderdb.py).

## DXT5nm detail-normal decode

`Nm_General_001` is BC3/DXT5 storage, but RGB is not a conventional XYZ normal.
The shader:

1. Multiplies its normal-map UVs by 8.
2. Samples green and alpha.
3. Decodes X from alpha and Y from green.
4. Reconstructs positive Z.
5. Transforms the tangent-space result through the TBN basis.
6. Adds it to the base vertex normal with weight `0.4`.
7. Normalizes the final vector.

Equivalent equations:

```text
x = alpha * 2 - 1
y = green * 2 - 1
z = sqrt(max(1 - x*x - y*y, 0))

detail_world = TBN * (x, y, z)
final_normal = normalize(base_normal + 0.4 * detail_world)
```

The `0.4` is not equivalent to setting a generic normal-map node's strength to
`0.4`; it weights the transformed detail vector before addition and final
normalization.

## Measured effect

For the decoded PC texture:

| Measurement | Value |
|---|---:|
| mean reconstructed Z | `0.94615` |
| mean final deviation from base normal | `4.68 degrees` |
| 95th percentile final deviation | `9.51 degrees` |
| maximum final deviation | `17.44 degrees` |
| incorrect raw-RGB mean Z | `-0.0110` |

The near-zero raw-RGB Z explains why a conventional RGB normal-map node looked
far too strong even with an arbitrary reduced strength.

## PC and Xbox consistency

After PC decode and Xbox untile/block conversion:

- green correlation is `1.0`;
- alpha correlation is `0.99937`;
- correlation with inverted Xbox green is `-1.0`;
- best orientation is direct, with no horizontal or vertical image flip;
- mean decoded-normal difference is `0.081 degrees`.

The compiled shader uses green directly. No shader-side green inversion is
present. If an importer flips mesh UV V when moving from DirectX to Blender,
it should not also invent a normal green inversion for this material.

## Blender implementation model

The implemented graph for the verified `Nm_General_001` binding:

1. Feed unscaled UVs to the diffuse texture.
2. Scale normal UVs by `(8, 8)`.
3. mark the normal image as non-color data;
4. separate green and alpha;
5. decode signed X/Y and reconstruct Z;
6. re-encode the tangent vector only as needed for Blender's Normal Map node;
7. use Normal Map strength `1.0` for the tangent-to-world transform;
8. multiply the resulting detail vector by `0.4`;
9. add Geometry Normal and normalize;
10. connect the normalized result to Principled BSDF Normal.

The importer caches one material per shader key and one native DDS image per
asset path. Each material stores its shader key, surface reference, binding
indices, reflected parameter names, source paths, inferred roles, color model,
and normal model as custom properties. All bindings receive image nodes even
when their meaning remains unclassified.

Role resolution combines two independent evidence sources:

- source texture families such as `Nm_`, `Dt_`, `Msk_`, `OcRGB`,
  `Occlusion`, roughness, specular, and common color suffixes;
- reflected pixel-shader parameter names from the exact material
  permutations.

An unsuffixed texture paired by path with an `_Nm` resource is treated as its
color partner. A remaining `texture_Texture` binding can be primary color only
after normal, mask, noise, occlusion, and detail families have been excluded.
Duplicate path/slot records from alternate render passes are retained as
metadata but do not create duplicate color layers.

## PC US_01 skinned-character materials

### Descriptor and database selection

`Characters/US/US_Models/US_01_Body_Mesh.dbx` contains two
`MeshShaderSetAsset` references. The first is the default appearance; the
second contains kit-upgrade overrides. A direct component import uses the
first set.

The high-level `Objects/Soldiers/US/Assault.dbx` entity supplies a `Meshes3p`
array linking `US_01_Body_Mesh`, `US_01_Head_Mesh`, and
`US_01_Headgear_Mesh`. Each entry can carry its own `MeshShaderSet` override
and `RandomGroup`. Assembly import resolves those overrides, retains random
groups as collection metadata, and binds all three LOD0 modules to the shared
147-bone `ske01` armature.

The shared `mp_common` archive contains the mesh, descriptor, skeleton, and
textures, but no DX11 shader database. Retail level shader databases duplicate
the shared character permutations. The importer deterministically indexes:

```text
Dist/win32/levels/mp_001/level-00.fbrb
Levels/mp_001/shaders/Dx11_Single.res
```

on demand for PC character materials. All 13 visible `US_01_Body` LOD0
surfaces resolve by exact database key. The full Assault assembly adds three
head and seven headgear subsets, including the face, eye, eyelash, teeth, and
headgear families absent from the body LOD. All 23 visible component materials
resolve in the retail integration scene.

### Verified visible binding families

Representative exact bindings are:

| Surface family | Source roles observed |
|---|---|
| `ArmStandard`, `LegStandard` | primary normal, repeated cloth-detail normal, dirt color, base texture, camouflage, repeated cloth detail, dirt mask, baked occlusion |
| `Gloves` | primary and cloth-detail normals, dirt color/mask, glove base, cloth detail, leather auxiliary, specular, baked occlusion |
| `MOLLE`, `Kits`, `Pouches` | primary and cloth-detail normals, base, repeated cloth detail, dirt color/mask, baked occlusion; MOLLE also binds a material mask |
| `Boots`, `Buckles`, `Straps`, pads, holster, grenades | primary normal where present, base color, dirt color/mask, baked occlusion, with source specular on selected families |
| Beretta attachment | dummy/base color, dirt color, and dirt mask; the inspected binding has no primary normal |

Primary-color choice is not "the first color-looking texture." The importer
scores remaining candidates against the surface name and its paired primary
normal. This selects `Glove_01` rather than the auxiliary `leather_C`, and
selects resources such as `Boots_01_LOW`, `AssaultKit_01`, and
`Beretta_dummy` when their shader surface names differ.

### Verified character UV declaration

The relevant skinned vertex shaders declare four texture-coordinate sources:

| Pixel input | Mesh byte offset | Blender layer |
|---|---:|---|
| `v10.xy` from `v6.xy` | 40 | `UVMap` |
| `v10.zw` from `v3.xy` | 16 | `UV1` |
| `v11.xy` from `v6.zw` | 44 | `UV2` |
| `v11.zw` from `v7.xy` | 48 | `UV3` |

This is why the generic stride-64 guess at bytes 24/28 was wrong for skinned
characters: those bytes are tangent-frame inputs. Primary color and normal
usually use `UVMap`; selected camouflage/detail paths use `UV1` or `UV2`;
dirt masks use `UV1`/`UV2`; baked occlusion uses `UV3`.

#### US_01 collapsed-coordinate correction

The declaration and DXBC assignments above are preserved as source metadata,
but the byte-16 field is not a usable 2D UV on the three reported retail
subsets:

- `LegStandard`: all 929 vertices satisfy `u == v`;
- MOLLE: all 1,603 vertices satisfy `u == v`;
- pouches: all 1,361 vertices satisfy `u == v`.

Every triangle therefore has zero area in that coordinate pair. Routing
cloth detail and camouflage through it produced the visible zigzag bands in
Blender. The importer now uses the nondegenerate byte-44 `UV2` layer for:

- LegStandard camouflage, cloth color/detail normal, and dirt mask;
- MOLLE cloth color/detail normal and dirt mask;
- pouches cloth color/detail normal and dirt mask.

The original byte-16 values remain available in `UV1` for source inspection.
This is an explicit Blender compatibility correction rather than a claim that
the still-unknown runtime interpretation of the auxiliary field has been
fully decoded.

Declared coordinates are decoded even when a channel is constant. The linked
head's eyelash subset verifies this distinction: zero span is valid for an
explicit stride-64 channel and must not trigger the generic heuristic's
"nonvarying UV" rejection.

The supplied external BF3/BF4 MaxScript references reinforce this decision
boundary: their mesh readers use explicit `Vert_Diffuse_UV` and
`Vert_Normals_UV` semantics and offsets, keep tangent/binormal fields
separate, and V-flip each recognized UV channel. Their standard `_d`/`_s`/`_n`
material setup does not reproduce BC2's layered shaders. See the
[external MaxScript audit](maxscript-reference-audit.md).

### Normal packing and layer arithmetic

The inspected `ps_5_0` permutations reconstruct the primary normal from red
and green:

```text
x = red * 2 - 1
y = green * 2 - 1
z = sqrt(max(1 - x*x - y*y, 0))
```

Cloth-detail normals use DXT5nm-style alpha/green storage. The shaders repeat
them by surface: 7x for `ArmStandard`, 8x for `LegStandard`, 10x for gloves,
5x for MOLLE and pouches, and 15x for kits. The importer decodes both packed
normals, transforms them through Blender normal-map nodes, adds the detail
deviation to the primary normal, and normalizes. This reproduces the verified
packing and repeated-detail relationship; it is labeled an approximation
because the game combines the tangent vectors before its complete lighting
calculation and some permutations weight detail with base alpha.

Representative color permutations also establish:

- dirt color is commonly sampled at 15x UV and multiplied by `2.5`;
- a separate source dirt map selects between dirt and the clean material;
- baked occlusion is sampled through the fourth UV channel and multiplies the
  final color;
- `ArmStandard` camouflage repeats `(2, 3)`;
- `LegStandard` camouflage repeats `(2, 4)`;
- cloth detail modulates the base/camouflage result.

The Blender graph preserves those source relationships. Frostbite uses
surface-specific dirt remaps, hard-coded tints, specular exponents, distance
terms, outdoor lighting, and alternate render permutations. Those parts are
represented conservatively with Principled roughness/specular settings and
are explicitly recorded as approximations in material custom properties.

### Validation result

The retail integration scene resolves 23/23 visible materials across body,
head, and headgear and loads 56 unique file-backed DDS images. The 13 body
subsets retain all four UV layers and connected Base Color graphs. Every
surface with a source primary normal has a connected packed-normal graph. All
three modules share one armature; materials, images, UV layers, modifiers,
component metadata, `StandIdle`, and `RunForward` persist after save/reopen.

## Standalone composite-vehicle materials

A standalone vehicle entity has no selected level from which to infer a DX11
database, while shared archives contain its mesh, shader descriptors, and
textures but not compiled level material records. The importer first reuses
already indexed `Dx11_Single.res` databases. It uses `MP_001` as the
deterministic shared-character source and, when required keys remain missing,
loads the verified `MP_004` database as a standalone modular fallback.
Databases are merged by case-insensitive material key, and their archives are
added to texture lookup precedence.

The AH60's `MP_004` records exactly match its composite mesh/shader keys. The
validated import resolves 11 visible surface families, including Main, Wreck,
metal, cockpit/interior, glass, lights, minigun, and blurred rotors, and loads
14 file-backed images. The material graph uses the same reflected texture-role
pipeline as complete maps. This solves source bindings, not vehicle runtime
behavior; rotor animation, damage switching, lighting constants, and exact
blend arithmetic remain outside the current scope.

### Verified AH60 Main, glass, interior, and minigun graphs

The earlier generic role pipeline recovered the correct `MP_004` material
keys and textures but misinterpreted several families. AH60 Main routed every
binding through byte-24 `UVMap`, `Glass` had no color-producing binding, the
pale `Interior_D` atlas was connected without the shader's dark scale, and the
channel-packed `MiniGun_C` texture was incorrectly promoted to Base Color
because of its `_C` suffix.

Retail pixel-shader disassembly establishes the following behavior:

| Surface | Pixel shaders | Verified relationship |
|---|---|---|
| AH60 Main | `1229`, `1792` | Blends `Ah60Blackhawk_C` to `Symbols_Us` by symbol alpha, adds the blue dirt channel plus a constant bias, applies `Ah60Blackhawk_D` modulation, and samples `Msk_Generic` at 15x for its outdoor-light term |
| AH60 Glass | `978`, `1135`, `2110` | Opacity combines a view-angle Fresnel term with the red channel of `DirtMaskRGB`; the lit permutations multiply reflected light by the same opacity |
| AH60 Interior | `174`, `910` | `Interior_D` supplies color and the direct diffuse term uses a `0.2` scale |
| AH60 CockpitInterior | `1538`, `1589` | Uses the same `Interior_D` atlas with a darker `0.05` direct diffuse scale |
| Minigun Main | `23`, `1869` | `Symbols_Us` supplies RGB/alpha color, `Msk_Generic` adds a repeated low-amplitude surface term, and `MiniGun_C` green controls specular response rather than color |

AH60 Main vertex shaders `428`, `554`, `748`, and `1310` agree on:

```text
pixel v6.xy <- vertex v2.zw <- byte 28 (UV1)
pixel v6.zw <- vertex v3.xy <- byte 32 (UV2)
pixel v7.xy <- vertex v5.xy <- byte 40 (UV3)
pixel v7.zw <- vertex v2.xy <- byte 24 (UVMap)
```

The recovered pre-light relationship is:

```text
base = lerp(sample(Ah60Blackhawk_C, UV1).rgb,
            sample(Symbols_Us, UV2).rgb,
            sample(Symbols_Us, UV2).a)
base += sample(DirtMaskRGB, UV3).b * 0.1 + 0.045
base *= lerp(1.0, sample(Ah60Blackhawk_D, UVMap).rgb * 2.0, 0.482)
lighting mask = sample(Msk_Generic, UV1 * 15).rgb
```

The imported Blender graph reproduces the recoverable pre-light color. The
generic mask remains attached at its verified coordinate and scale, while its
outdoor-light interaction remains Blender-native. On the reported
`01_lod0_WreckPartTail_Main.001` piece, byte-24 has 280 degenerate UV
triangles out of 722; byte-28 has none. That is valid source data for
different shader inputs, not evidence that LOD1 was selected.

The recovered minigun pre-light color is:

```text
base = lerp(0.072, sample(Symbols_Us, UV1).rgb,
                    sample(Symbols_Us, UV1).a)
base += sample(Msk_Generic, UVMap * 13).rgb * 0.006
specular mask = sample(MiniGun_C, UVMap).g
```

Paired retail vertex shaders `1400` and `1583` both write
`o6.xyzw = v2.zwxy`. The packed stride-48 `TEXCOORD3` input places the
byte-24 half-float pair in `v2.xy` (`UVMap`) and the byte-28 pair in
`v2.zw` (`UV1`). Consequently pixel input `v6.xy`, used by `Symbols_Us`,
comes from `UV1`, while `v6.zw`, used by `Msk_Generic` and `MiniGun_C`,
comes from `UVMap`. This swizzle is why treating all three bindings as
secondary UVs produces incorrect minigun texturing.

The source specular exponent is `20`. Blender approximates that response with
Principled roughness `0.3` and feeds `MiniGun_C` green to Specular IOR Level.
The glass graph uses Principled transmission with Fresnel plus dirt-red
opacity. These graphs preserve the exact source texture roles, UV channels,
repeat factor, and immediate constants; Frostbite's outdoor-light buffers and
reflection environment remain Blender-native approximations.

### Verified representative map families

FXC disassembly of retail `MP_001` permutations established these patterns:

| Family | Observed bindings | Shader behavior relevant to Blender |
|---|---|---|
| Background trees | `texture_Texture4` ambient occlusion, `texture_Texture` tree atlas | atlas color and alpha are sampled from the source UV; alpha is tested at `0.5`; ambient occlusion is sampled separately |
| Jungle bark | `texture_Texture` normal, `texture_Texture2` bark color, `texture_Texture3` noise | normal and color use the same UV; noise controls distance/fade behavior rather than Base Color |
| Jungle foliage | `texture_Texture` leaf atlas, `texture_Texture2` noise | atlas alpha participates in a cutout test at `0.2`; noise contributes to the fade threshold |
| Layered props | `texture_Texture` object `OcRGB`, reflected `Layer*Detail*` textures, optional mask and normal atlases | detail colors are combined under object-map channel control; object alpha supplies occlusion in the inspected permutation; one detail layer uses a repeated UV and the optional mask uses world-space X/Z |

The Blender layered graph reproduces the recoverable high-level relationship:
it mixes reflected detail-color layers with OcRGB channels and multiplies by
source occlusion. Identified OcRGB object maps use the retained secondary mesh
channel `UV1`; ordinary color and detail bindings use `UVMap` unless stronger
shader evidence selects another source. Exact hard-coded tints, world-space
mask coordinates, UV scales, lighting, and every permutation remain
approximations. Identified foliage/cutout families use source color alpha with
Blender's dithered surface mode; this does not claim exact parity with each
DXBC threshold.

`Decal_Atlas_001` is explicitly classified as `DECAL` and retained as an
unconnected source node until its atlas selectors and coordinates are decoded.
It must not be promoted to primary color merely because no ordinary color
binding exists. Sampling the complete atlas through a repeating detail UV
produced the reported red/white striping on GasSilo and IND_Silo_Medium; their
base graph now comes from the reflected detail layers controlled by OcRGB.

In the saved `MP_001` validation scene, 418 material keys resolve exactly. Of
those, 417 produce a connected Base Color graph. The remaining binding-only
material is an invisible-wall shader with no texture binding.

Other DXT5 textures classified as normals use an explicitly labeled heuristic
alpha/green DXT5nm decode at unit UV scale. Non-DXT5 normal candidates use a
standard RGB tangent-normal node. Missing keys, textures, and undecidable
subset/surface matches are written to the map Diagnostics text.

## Sparse shader-set overrides

`MeshShaderSet` overrides are not always complete surface tables. The tested
`IND_SmallFactory` placement override contains only three cheap-metal LOD
surfaces, while the mesh's default set contains the building's other surface
families. The resolver merges an override over the default by normalized
surface name instead of replacing the entire set.

This preserves the intended cheap-metal substitutions while resolving all
eleven visible SmallFactory LOD0 subsets. It also eliminates the magenta
diagnostic materials previously created for the omitted Glass, Template, Wall,
Wood, Concrete, Ground, grate, diamond plate, and corrugated-metal surfaces.

## Terrain material approximation

The decoded 4096 x 4096 `MP_001` physical-material index map names
`defaultmaterial`, Grass, Dirt, Tarmac, Gravel, Stone, and SeaBed. Blender
stores the indices in a native file-backed L8 DDS with nearest sampling and
selects source textures recovered from the level shader database:

- jungle ground for the default class;
- grass close-up for Grass;
- soil/ground-mud families for Dirt;
- asphalt/tarmac families for Tarmac;
- dry gravel for Gravel;
- cliff/stone/rubble families for Stone;
- rubble-sand/seabed families for SeaBed.

The result is marked `resolved terrain material map`, not an exact shader
reproduction. The 16 m detail repeat is estimated. Full decals, mask regions,
`MaskTileAtlas`, hard-coded constants, and Frostbite's precise blend arithmetic
remain unresolved.

## MaxScript material boundary

The audited BF3 mesh scripts create a standard material by looking for PNG
files with `_d`, `_s`, and `_n` suffixes. The BF4 script performs similar DDS
filename matching in the mesh directory or a `textures` child directory.
None parses `MeshShaderSet`, DBX texture references, shader-database records,
DXBC reflection, constants, color space, packed channels, or layered shader
arithmetic.

Those scripts therefore provide no material behavior that supersedes the
retail BC2 shader evidence documented here. Their naming convention can be a
last-resort research hint only; it must not replace exact resource bindings.
See the [external MaxScript audit](maxscript-reference-audit.md).

## Generalization work still needed

Do not globally classify every DXT5 resource as DXT5nm. A general material
resolver needs to:

- recover exact UV sources, constants, and swizzles per shader permutation;
- distinguish every color, masks, specular, terrain, and normal role;
- reproduce alpha-test thresholds and two-sided behavior from shader evidence;
- retain variant-specific behavior instead of applying one universal graph.

Shader bytecode and extracted game resources should remain local research
inputs. Commit summaries and independently written format facts, not copied
bytecode or game payloads.
